# Decisioni di progetto

Registro sintetico delle scelte (ADR leggeri): contesto, decisione, alternative scartate.
Stato: **ACCETTATA** (in uso) · **PROPOSTA** (sarà confermata nella fase indicata).

| ID | Decisione | Stato | Motivo | Alternative scartate |
|---|---|---|---|---|
| D-01 | Workload: Online Boutique **v0.10.7** | ACCETTATA | Consigliata dal PDF; 11 microservizi in 5 linguaggi, HTTP + gRPC, chart Helm disponibile | Altre app demo (es. Sock Shop): equivalenza da dimostrare senza vantaggi |
| D-02 | Cluster locale **kind** a nodo singolo, node image fissata per digest | ACCETTATA | Leggero, basato su Docker, usato anche in CI; confermato accettabile da Kiratech | minikube (più pesante), k3d (valido); OpenShift Local (RAM insufficiente) |
| D-03 | Packaging con il **chart Helm** upstream e un file di values per ambiente | ACCETTATA | Differenze tra ambienti esplicite e revisionabili; Redis già fissato per digest nel chart | Kustomize (valido, ma uno strumento solo); manifest `release/` (Redis senza digest) |
| D-04 | Ambienti **dev** e **prod** come namespace dello stesso cluster; un file di values comune più uno piccolo per ambiente | ACCETTATA | Ammesso dal PDF; sta nella RAM (dev + prod + piattaforma ≈ 2,4 GiB sul nodo); il diff tra gli ambienti mostra solo parametri (repliche, host, loadgenerator) | Cluster separati (realistico ma troppo pesante in locale, limite L1 in `SECURITY.md`); un file completo per ambiente (duplicazione e derive) |
| D-05 | Build solo del servizio modificato (**frontend**), immagine `frontend:v0.10.7-kt.1` caricata in kind; stessa immagine in dev e prod | ACCETTATA | Compilare 11 servizi in 5 linguaggi non aggiunge valore; il frontend è dove andrà la metrica | Build di tutti i servizi; registry locale (in più da gestire; il push su GHCR arriva con la CI) |
| D-06 | Metrica applicativa `/metrics` Prometheus nel frontend | PROPOSTA (F4) | Il frontend vede tutto il traffico esterno | Metriche solo infrastrutturali |
| D-07 | Password di Redis come Secret cifrato in Git (**Sealed Secrets** 0.41.2), diversa per ambiente; chiave privata salvata a mano fuori da Git | ACCETTATA | Compatibile con GitOps, nessun secret in chiaro; cartservice la usa **senza modifiche al codice** | External Secrets + vault (troppo per un ambiente locale); SOPS (chiavi da distribuire a ogni persona) |
| D-08 | CI con GitHub Actions, CD GitOps con Argo CD; la CI non accede mai al cluster (modello *pull*) | ACCETTATA (F3) | Integrazione con il fork e GHCR; Argo CD è lo standard di fatto e la sua UI rende leggibile la demo; il cluster locale non va esposto né dato in mano alla CI | Flux (valido, senza UI inclusa); deploy diretto da pipeline (*push*: credenziali del cluster in CI, cluster raggiungibile da Internet) |
| D-09 | Krateo: valutazione con blueprint e YAML concettuale; PoC se le risorse bastano | ACCETTATA | Il PDF non rende obbligatoria l'integrazione; confermato da Kiratech | Integrazione completa (RAM limitata) |
| D-10 | Nessun worker/broker nell'app: gap dichiarato + CronJob di smoke test come componente batch | PROPOSTA (fase runbook) | Copre il componente "worker" senza inventare funzioni; spostata nella fase di troubleshooting, dove lo smoke test serve | Aggiungere un broker (fuori scopo) |
| D-13 | Esposizione del frontend: **Ingress** servito da **Traefik** 3.7 su `hostPort` 80/443, porte del nodo kind pubblicate su `127.0.0.1` | ACCETTATA | Porta fissa raggiungibile dal browser di Windows, nessun `sudo`, nessun processo esterno; il PDF chiede un Ingress | cloud-provider-kind (indicato dalla doc kind, ma su WSL2 richiede `sudo`, un processo sempre acceso e porte effimere); ingress-nginx (ritirato a marzo 2026, senza patch di sicurezza); Gateway API (evoluzione futura, citata) |
| D-14 | Repository nel filesystem Linux di WSL | ACCETTATA | Sul disco Windows montato in WSL git non può impostare i permessi (`chmod … Operation not permitted`) | Opzione `metadata` del mount (sudo, I/O lento) |
| D-15 | GitHub Actions disattivato sul fork fino alla F3, poi riattivato senza i workflow upstream (rimossi dal fork) | ACCETTATA (aggiornata in F3) | I workflow upstream presuppongono l'infrastruttura Google Cloud | Disattivare i singoli workflow (non ancora registrati da GitHub) |
| D-17 | Estensioni del chart come **opzioni disattivate di default** (Ingress, ConfigMap, RBAC, auth Redis, immagine del frontend, token non montato) | ACCETTATA | Upstream invariato per chi non le attiva (verificato con `helm template` + `diff`); modifiche piccole e tracciate in `CHANGES.md` | Chart nuovo scritto da zero (più lavoro, si perde l'allineamento all'upstream); post-render o patch Kustomize sopra Helm (due strumenti) |
| D-18 | RBAC: **nessun permesso** ai ServiceAccount applicativi; Role `ops-readonly` per il gruppo `boutique-operators` | ACCETTATA | I servizi non usano l'API; gli operatori L2 devono leggere pod, log ed eventi, non Secret né `exec` | ClusterRole `view` predefinito (include più risorse del necessario) |
| D-19 | Frontend con hook `preStop` di 5 s (azione `sleep` eseguita dal kubelet) | ACCETTATA | Misurato: durante un rolling update di prod 3 richieste su 417 fallivano (502/timeout) perché Traefik inviava ancora traffico al pod in chiusura; con il `preStop` 0 su 399 | `preStop` con `exec sleep` (l'immagine distroless non ha `sleep`); gestione di SIGTERM nel codice Go (modifica applicativa non necessaria) |
| D-20 | Lease di leader election più lunghi (60s/40s/5s) per controller-manager e scheduler nel cluster kind | ACCETTATA | Su WSL2 i pull di molte immagini rallentano etcd; i due componenti perdevano il lease e ripartivano (5 restart ciascuno); con i lease lunghi 0 restart a parità di carico | Pre-caricare le immagini (utile ma non sufficiente da solo); etcd su tmpfs (dati persi al riavvio del nodo) |
| D-21 | Supply chain della CI: action fissate per **SHA completo**, versioni dei tool fissate (kubeconform con checksum), Trivy tramite `trivy-action` v0.36.0 (successiva all'incidente) con Trivy v0.76.1 | ACCETTATA | Nel marzo 2026 i tag di `trivy-action` sono stati spostati su codice malevolo (CVE-2026-33634): un tag si può spostare, uno SHA no | Tag di versione (`@v4`); niente scansione (R-09 chiede una pipeline di qualità; la scansione è il controllo di sicurezza dell'immagine) |
| D-22 | Tag dell'immagine **immutabili**: la CI pubblica solo se il tag non esiste; per nuovo codice si alza il tag in `deploy/values-common.yaml` con un commit | ACCETTATA | Un tag che cambia contenuto rende impossibile sapere cosa gira e rompe il rollback; il commit del tag è anche la prova del GitOps | Tag = SHA del commit scritto dalla CI su `main` (un bot che scrive su `main`); Argo CD Image Updater (componente in più per un solo servizio) |

Le decisioni D-11, D-12 e D-16 riguardano l'ambiente personale di lavoro (RAM di WSL, demo dal vivo, organizzazione degli appunti) e non il repository.
