# Decisioni di progetto

Registro sintetico delle scelte (ADR leggeri): contesto, decisione, alternative scartate.
Stato: **ACCETTATA** (in uso) · **PROPOSTA** (sarà confermata nella fase indicata).

| ID | Decisione | Stato | Motivo | Alternative scartate |
|---|---|---|---|---|
| D-01 | Workload: Online Boutique **v0.10.7** | ACCETTATA | Consigliata dal PDF; 11 microservizi in 5 linguaggi, HTTP + gRPC, chart Helm disponibile | Altre app demo (es. Sock Shop): equivalenza da dimostrare senza vantaggi |
| D-02 | Cluster locale **kind** a nodo singolo, node image fissata per digest | ACCETTATA | Leggero, basato su Docker, usato anche in CI; confermato accettabile da Kiratech | minikube (più pesante), k3d (valido); OpenShift Local (RAM insufficiente) |
| D-03 | Packaging con il **chart Helm** upstream e un file di values per ambiente | ACCETTATA | Differenze tra ambienti esplicite e revisionabili; Redis già fissato per digest nel chart | Kustomize (valido, ma uno strumento solo); manifest `release/` (Redis senza digest) |
| D-04 | Ambienti **dev** e **prod** come namespace dello stesso cluster; un file di values comune più uno piccolo per ambiente | ACCETTATA | Ammesso dal PDF; sta nella RAM (dev + prod + piattaforma ≈ 2,4 GiB sul nodo); il diff tra gli ambienti mostra solo parametri (repliche, host, loadgenerator) | Cluster separati (realistico ma troppo pesante in locale, limite L1 in `SECURITY.md`); un file completo per ambiente (duplicazione e derive) |
| D-05 | Build solo del servizio modificato (**frontend**), immagine `frontend:v0.10.7-kt.1` (dalla F4 `kt.2`, con le metriche) caricata in kind; stessa immagine in dev e prod | ACCETTATA | Compilare 11 servizi in 5 linguaggi non aggiunge valore; il frontend è dove andrà la metrica | Build di tutti i servizi; registry locale (in più da gestire; il push su GHCR arriva con la CI) |
| D-06 | Metrica applicativa: endpoint `/metrics` nel frontend con **client_golang**, su una **porta separata** (9090), raccolto da Prometheus tramite `ServiceMonitor` | ACCETTATA (F4) | L'upstream non espone metriche Prometheus (solo tracing OTel, spento). Il frontend vede ogni richiesta e ogni ordine: richieste, latenze per rotta e ordini completati bastano per una dashboard RED. Sulla 8080 `/metrics` sarebbe pubblicato dall'Ingress | OTel SDK + collector verso Prometheus (più componenti e RAM); metriche solo da Traefik (nessuna metrica di business); `/metrics` sulla 8080 |
| D-07 | Password di Redis come Secret cifrato in Git (**Sealed Secrets** 0.41.2), diversa per ambiente; chiave privata salvata a mano fuori da Git | ACCETTATA | Compatibile con GitOps, nessun secret in chiaro; cartservice la usa **senza modifiche al codice** | External Secrets + vault (troppo per un ambiente locale); SOPS (chiavi da distribuire a ogni persona) |
| D-08 | CI con GitHub Actions, CD GitOps con **Argo CD 3.6.1** (chart 10.18.0); la CI non accede mai al cluster (modello *pull*); dev con sync automatica, prod con sync manuale | ACCETTATA (F3) | Integrazione con il fork e GHCR; Argo CD è lo standard di fatto e la sua UI rende leggibile la demo; il cluster locale non va esposto né dato in mano alla CI. La 3.6 è la prima linea testata con Kubernetes 1.37 ([versioni testate](https://argo-cd.readthedocs.io/en/stable/operator-manual/tested-kubernetes-versions/)) | Flux (valido, senza UI inclusa); deploy diretto da pipeline (*push*: credenziali del cluster in CI, cluster raggiungibile da Internet); App of Apps / ApplicationSet (non servono con due ambienti) |
| D-09 | Krateo: valutazione, golden path e **PoC del solo motore** (core-provider), portale escluso | ACCETTATA (F6) | Il PDF non rende obbligatoria l'integrazione; la piattaforma completa chiede 12 vCPU / 16 GiB; il motore sta in ~0,4 GiB ([KRATEO](KRATEO.md)) | Krateo completo; quickstart in un secondo cluster kind (stesse risorse, e sarebbe una demo di Krateo, non della soluzione) |
| D-10 | Nessun worker/broker nell'app: gap dichiarato + CronJob di smoke test come componente batch | PROPOSTA (fase runbook) | Copre il componente "worker" senza inventare funzioni; spostata nella fase di troubleshooting, dove lo smoke test serve | Aggiungere un broker (fuori scopo) |
| D-13 | Esposizione del frontend: **Ingress** servito da **Traefik** 3.7 su `hostPort` 80/443, porte del nodo kind pubblicate su `127.0.0.1` | ACCETTATA | Porta fissa raggiungibile dal browser di Windows, nessun `sudo`, nessun processo esterno; il PDF chiede un Ingress | cloud-provider-kind (indicato dalla doc kind, ma su WSL2 richiede `sudo`, un processo sempre acceso e porte effimere); ingress-nginx (ritirato a marzo 2026, senza patch di sicurezza); Gateway API (evoluzione futura, citata) |
| D-14 | Repository nel filesystem Linux di WSL | ACCETTATA | Sul disco Windows montato in WSL git non può impostare i permessi (`chmod … Operation not permitted`) | Opzione `metadata` del mount (sudo, I/O lento) |
| D-15 | GitHub Actions disattivato sul fork fino alla F3, poi riattivato senza i workflow upstream (rimossi dal fork) | ACCETTATA (aggiornata in F3) | I workflow upstream presuppongono l'infrastruttura Google Cloud | Disattivare i singoli workflow (non ancora registrati da GitHub) |
| D-17 | Estensioni del chart come **opzioni disattivate di default** (Ingress, ConfigMap, RBAC, auth Redis, immagine del frontend, token non montato) | ACCETTATA | Upstream invariato per chi non le attiva (verificato con `helm template` + `diff`); modifiche piccole e tracciate in `CHANGES.md` | Chart nuovo scritto da zero (più lavoro, si perde l'allineamento all'upstream); post-render o patch Kustomize sopra Helm (due strumenti) |
| D-18 | RBAC: **nessun permesso** ai ServiceAccount applicativi; Role `ops-readonly` per il gruppo `boutique-operators` | ACCETTATA | I servizi non usano l'API; gli operatori L2 devono leggere pod, log ed eventi, non Secret né `exec` | ClusterRole `view` predefinito (include più risorse del necessario) |
| D-19 | Frontend con hook `preStop` di 5 s (azione `sleep` eseguita dal kubelet) | ACCETTATA | Misurato: durante un rolling update di prod 3 richieste su 417 fallivano (502/timeout) perché Traefik inviava ancora traffico al pod in chiusura; con il `preStop` 0 su 399 | `preStop` con `exec sleep` (l'immagine distroless non ha `sleep`); gestione di SIGTERM nel codice Go (modifica applicativa non necessaria) |
| D-20 | Lease di leader election più lunghi (60s/40s/5s) per controller-manager e scheduler nel cluster kind | ACCETTATA | Su WSL2 i pull di molte immagini rallentano etcd; i due componenti perdevano il lease e ripartivano (5 restart ciascuno); con i lease lunghi 0 restart a parità di carico | Pre-caricare le immagini (utile ma non sufficiente da solo); etcd su tmpfs (dati persi al riavvio del nodo) |
| D-21 | Supply chain della CI: action fissate per **SHA completo**, versioni dei tool fissate (kubeconform con checksum), Trivy tramite `trivy-action` v0.36.0 (successiva all'incidente) con Trivy v0.76.1 | ACCETTATA | Nel marzo 2026 i tag di `trivy-action` sono stati spostati su codice malevolo (CVE-2026-33634): un tag si può spostare, uno SHA no | Tag di versione (`@v4`); niente scansione (R-09 chiede una pipeline di qualità; la scansione è il controllo di sicurezza dell'immagine) |
| D-22 | Tag dell'immagine **immutabili**: la CI pubblica solo se il tag non esiste; per nuovo codice si alza il tag in `deploy/values-common.yaml` con un commit | ACCETTATA | Un tag che cambia contenuto rende impossibile sapere cosa gira e rompe il rollback; il commit del tag è anche la prova del GitOps | Tag = SHA del commit scritto dalla CI su `main` (un bot che scrive su `main`); Argo CD Image Updater (componente in più per un solo servizio) |
| D-23 | **AppProject** `boutique` con privilegi minimi (un solo repo, destinazioni dev/prod, nessuna risorsa cluster-scoped); namespace creati da `install.sh` (strato di piattaforma), non da Argo CD (`CreateNamespace` non usato) | ACCETTATA (F3) | Il progetto `default` permette tutto (qualunque repo, cluster, risorsa); un errore in Git non può creare ClusterRole o toccare altri namespace | Progetto `default`; `CreateNamespace=true` (richiederebbe di permettere i Namespace, cioè risorse cluster-scoped) |
| D-24 | DNS: `ndots: 1` solo sul **repo-server** di Argo CD | ACCETTATA (F3) | Il router di casa risponde `127.0.0.1` per i nomi con il suo dominio di ricerca (es. `github.com.<dominio-del-router>`); con `ndots: 5` il pod li prova prima del nome vero e git fallisce (`dial tcp 127.0.0.1:443: connection refused`). Con `ndots: 1` i nomi con un punto sono cercati subito come assoluti | Cambiare il DNS di WSL o del router (fuori dal repo, non riproducibile); `ndots: 1` su tutti i pod (non serve: solo il repo-server esce verso Internet) |
| D-25 | Traefik scrive `127.0.0.1` nello **stato degli Ingress** (`ingressEndpoint.ip`) | ACCETTATA (F3) | Argo CD considera un Ingress pronto solo con `status.loadBalancer.ingress` valorizzato; copiandolo dal Service ClusterIP resta vuoto e l'Application resta `Progressing`. `127.0.0.1` è il dato vero: si entra da localhost | Health check personalizzato che ignora gli Ingress (nasconde il sintomo); Service LoadBalancer con cloud-provider-kind (vedi D-13) |
| D-26 | Aggiornamento di Traefik con `maxSurge: 0`, `maxUnavailable: 1` | ACCETTATA (F3) | Con `hostPort` su un solo nodo il pod nuovo resta `Pending` finché il vecchio occupa le porte 80/443 | Default `maxSurge: 1` (upgrade bloccato); più nodi (RAM) |
| D-27 | `install.sh` installa solo la **piattaforma**; l'app la applica Argo CD. Prod riceve una sync iniziale solo alla prima installazione, poi solo promozioni manuali | ACCETTATA (F3) | Un solo responsabile per lo stato dell'app (Git tramite Argo CD); lo script resta idempotente e non scavalca la promozione | `helm upgrade` dell'app nello script (due strumenti che scrivono le stesse risorse, drift continuo) |
| D-28 | Monitoring con **kube-prometheus-stack** installato da `install.sh` (strato piattaforma), ridotto per un portatile: niente Alertmanager, niente target di control-plane irraggiungibili su kind, retention 2 giorni | ACCETTATA (F4) | Operator + Prometheus + Grafana + exporter in un chart, ServiceMonitor accanto all'app. Crea CRD e ClusterRole: come Application violerebbe l'AppProject `boutique` (D-23) | Prometheus e Grafana con chart separati (scrape configurato a mano); Loki per i log (R-11 chiede log strutturati, `kubectl logs \| jq` basta); monitoring come Application di Argo CD con un secondo AppProject (rimandato) |
| D-29 | Probe: `startupProbe` e timeout di 3 s per tutti i servizi (opzione `probes.tuning`) | ACCETTATA (F4) | Riprodotto con `docker restart` del nodo: con 24 pod che partono insieme la liveness (timeout 1 s) uccideva currencyservice, paymentservice, recommendationservice e Redis. La startupProbe protegge solo l'avvio; dopo, la liveness resta stretta (5 errori di fila prima del riavvio: 25-75 s secondo il `periodSeconds` del servizio) | Alzare `initialDelaySeconds` (ritardo fisso anche quando non serve); togliere la liveness (un processo bloccato non verrebbe mai riavviato); togliere i limiti di CPU |
| D-30 | Guasti di prova solo in dev, con la **sync automatica sospesa** per il tempo del guasto (`scripts/fault.sh`); il ripristino riattiva la sync e Argo CD riporta tutto a Git | ACCETTATA (F5) | Con `selfHeal` un guasto fatto a mano sparisce in pochi secondi; si toccano solo risorse gestite da Argo CD, così "ridare il controllo a Git" è anche il rimedio | Chaos Mesh / Litmus (un operatore e CRD in più, RAM); guasti in prod |
| D-31 | **Rollback**: normale = `git revert` + merge (dev e prod); emergenza in prod = History and rollback di Argo CD, seguito sempre dal revert; mai `kubectl rollout undo`; `helm rollback` solo per la piattaforma | ACCETTATA (F5) | Eseguiti tutti e tre (PR #10-#13): revert in dev 3 min 15 s (quasi tutto polling), history in prod in 4 s, `rollout undo` annullato da `selfHeal` in 8 s. La history è vietata con la sync automatica (codice di Argo CD v3.6.1) | Solo `helm rollback` (l'app non è una release Helm); rollback dalla history anche in dev (impossibile con auto-sync) |
| D-32 | Prerequisito dell'host: `fs.inotify.max_user_instances=512` (persistente in `/etc/sysctl.d/`) | ACCETTATA (F6) | Con il default 128 il core-provider di Krateo andava in crash (`too many open files`): il nodo kind condivide il kernel e il limite con kubelet, Argo CD e Prometheus. Valore raccomandato da kind (known issues); `krateo-poc.sh` lo controlla | Ridurre i componenti (il problema torna al primo controller in più); impostarlo solo a runtime (si perde al riavvio di WSL) |
| D-33 | DNS dei pod di Krateo: `ndots:1` con una **MutatingAdmissionPolicy** sui namespace con la label `boutique.kiratech.local/dns-ndots-1=true` | ACCETTATA (F6) | Stessa causa di D-24, ma qui i pod che escono verso ghcr.io li crea Krateo a runtime e il chart non ha valori `dnsConfig`. API nativa, stabile dalla 1.36, dichiarativa, limitata a due namespace. `JSONPatch` perché `dnsConfig.options` è una lista atomica | Patch a mano dei Deployment (persa al primo `helm upgrade`); CoreDNS cluster-wide (esporrebbe il dominio della rete); Kyverno (un operatore in più) |
| D-34 | Golden path Krateo **sopra** Argo CD: la Composition crea solo il namespace e un'Application (AppProject `tenants`, namespace `team-*`); il chart è pubblicato come OCI su GHCR dalla CI, versioni immutabili per convenzione della CI (GHCR permetterebbe di sovrascrivere un tag); la CI controlla che Chart.yaml e CompositionDefinition abbiano la stessa versione | ACCETTATA (F6) | Un solo proprietario per ogni risorsa: Krateo la richiesta, Argo CD l'app (restano history, rollback, drift). È anche il modello del blueprint ufficiale `github-scaffolding-lifecycle`. Il chart upstream non si tocca | Composition che installa l'app direttamente con Helm (due riconciliatori sull'app); `values.schema.json` nel chart upstream (espone tutti i values); `.tgz` in una release GitHub |

Le decisioni D-11, D-12 e D-16 riguardano l'ambiente personale di lavoro (RAM di WSL, demo dal vivo, organizzazione degli appunti) e non il repository.
